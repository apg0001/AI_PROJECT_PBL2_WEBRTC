# 01. Requirement 정의

> 상태: v1.0 (1주차) · 관련 이슈 #3 · 구현·측정 결과에 따라 갱신한다.

## 1. 해결할 문제

A사의 설비에 이상이 생기면 현장 작업자가 사진·동영상을 메신저로 보내고 전화로 설명한다. 사진 몇 장으로는 상황이 정확히 전달되지 않아서, 단순한 문제에도 엔지니어가 현장에 출장 가는 일이 생긴다.

**목표:** 설치 없이 웹 브라우저만으로 현장 작업자와 원격 전문가를 실시간으로 연결해, 전문가가 영상을 보며 말과 포인터로 작업을 지시할 수 있게 한다.

## 2. 사용자와 사용 환경

| 구분 | 현장 작업자 (Field) | 원격 전문가 (Expert) |
|---|---|---|
| 단말 | Smartphone (Android Chrome, iOS Safari) | PC 또는 Tablet (Chrome, Safari, Edge) |
| 네트워크 | 공장 Wi-Fi, LTE/5G. 이동 중 전환 가능 | 회사·가정 Wi-Fi 또는 유선 |
| 작업 조건 | 한 손 또는 양손으로 작업. 화면 조작 최소화. 소음 있음 | 책상 앞. 키보드·마우스 사용 가능 |
| 하는 일 | 후면 카메라로 장비를 비춤, 음성 설명, 지시 수행, 장비 정보 전달 | 영상 확인, 음성 지시, 화면 위 포인터 지시, 텍스트 지시 |
| 기술 수준 | 낮다고 가정. URL을 열고 권한만 허용하면 되어야 함 | 보통 |

## 3. User Scenario

### 기본 흐름

1. 현장 작업자가 설비 이상을 발견하고 원격지원 링크(Room 주소)를 연다.
2. 브라우저가 카메라·마이크 권한을 묻고, 작업자가 허용한다.
3. 작업자가 Room에 입장해 전문가를 기다린다. 화면에 "전문가 대기 중"이 표시된다.
4. 전문가가 같은 Room에 입장한다.
5. 두 브라우저가 연결된다. 전문가 화면에 현장 후면 카메라 영상이 나오고, 양방향 음성이 연결된다.
6. 작업자가 장비 ID·Error Code를 전달한다(텍스트 또는 장비 상태 메시지).
7. 전문가가 영상을 보며 음성으로 설명하고, 확인할 부위를 화면에서 클릭해 포인터로 가리킨다.
8. 중요한 지시("전원 OFF 후 작업하세요")는 텍스트로도 보내고, 현장 화면에서 수신을 확인한다.
9. 문제가 해결되면 어느 한쪽이 종료한다. 상대 화면에 종료가 표시된다.

### 예외 흐름

| ID | 상황 | 시스템 동작 |
|---|---|---|
| E1 | 카메라·마이크 권한 거부 | 원인과 재시도 방법을 안내한다. 음성만 또는 영상만으로도 진행 가능 |
| E2 | Room이 가득 참 (이미 2명) | 입장을 거부하고 안내한다 |
| E3 | P2P 연결 실패 (ICE failed) | 어느 단계에서 실패했는지 표시하고 로그를 남긴다. TURN이 필요한 환경일 수 있음을 안내한다 |
| E4 | 이동 중 네트워크 불안정·전환 | "연결 불안정" 상태를 표시하고 복구를 시도한다 (#24) |
| E5 | 상대방 이탈 (탭 종료, 배터리) | "상대가 나갔습니다"를 표시하고 재입장을 기다린다 |
| E6 | 시그널링 서버 연결 끊김 | 이미 연결된 P2P 통화는 유지된다. 새 연결과 재연결만 불가 |

## 5. 교환 데이터와 요구 특성

데이터의 의미에 따라 요구가 다르므로 전달 방법도 달라야 한다(과제 명세 §12-13).

| 데이터 | 방향 | 빈도 | 지연 요구 | 신뢰성 | 순서 | 오래된 값의 가치 | 전달 방법 (→ 04 기술 결정) |
|---|---|---|---|---|---|---|---|
| Video | 현장 → 전문가 | 연속 15~30fps | 매우 낮음 | 손실 허용 (재전송보다 다음 프레임) | 필요 | 없음 | MediaStream Video Track |
| Audio | 양방향 | 연속 | 매우 낮음 | 손실 허용 | 필요 | 없음 | MediaStream Audio Track |
| Pointer 좌표 | 전문가 → 현장 | 이동 중 30~60회/초 | 낮음 | 손실 허용 | 불필요 | 없음 (최신 값만 의미) | DataChannel `pointer` (unreliable) |
| 텍스트 메시지 | 양방향 | 가끔 | 보통 | 반드시 도착 | 필요 | 있음 | DataChannel `control` (reliable) |
| 작업 지시 | 전문가 → 현장 | 가끔 | 보통 | 반드시 도착 + 수신 확인 | 필요 | 있음 | DataChannel `control` + `ack` |
| 장비 상태 (ID, Error Code) | 현장 → 전문가 | 연결 시 + 변경 시 | 보통 | 반드시 도착 | 필요 | 있음 | DataChannel `control` |
| 연결 정보 (SDP, ICE) | 양방향 | 연결 시 | 보통 | 반드시 도착 | 필요 | 연결 전 단계 | Signaling (WebSocket) |

## 6. 품질 속성 (비기능 요구사항)

목표값은 **가설**이며, 측정(#21, #22) 후 근거와 함께 확정한다.

| ID | 속성 | 요구 | 초기 목표 (가설) | 근거 |
|---|---|---|---|---|
| NFR-01 | 실시간성 | 대화가 끊기지 않아야 한다 | Glass-to-Glass 지연 중앙값 ≤ 400ms | ITU-T G.114: 단방향 지연 400ms를 넘으면 대화형 통신에 부적합 |
| NFR-02 | 연결성 | 다른 네트워크에서도 연결되어야 한다 | 시험 조합의 성공률 기록, 실패 원인 100% 설명 | 과제 명세 §8 "1,000명 중 몇 명이 연결되는가" |
| NFR-03 | 연결 시간 | 지원 요청 후 빨리 연결되어야 한다 | Join → connected 중앙값 ≤ 3초 (동일 LAN) | 사용자 대기 체감 |
| NFR-04 | 품질 | 전문가가 볼트·계기판 숫자를 읽을 수 있어야 한다 | 정상 망 720p 이상, 열악한 망에서도 영상 정지 없이 움직임 확인 | 과제 명세 §10-11 (화질보다 끊김 없는 쪽이 우선) |
| NFR-05 | 안정성 | 장애 시 사용자가 상태를 알고 대응할 수 있어야 한다 | 모든 연결 상태 변화를 화면에 표시 | 과제 명세 §17 |

## 7. 제약과 가정

- 1:1 연결만 다룬다 (다자간은 #27 분석만).
- STUN은 공용 서버(`stun.l.google.com:19302`)를 쓴다.
- TURN은 자체 구축하지 않는다. P2P가 실패하는 환경에서는 호스팅 TURN 적용을 검토한다 (#38).
- 시그널링 서버는 개발자 PC에서 실행하고 ngrok으로 외부에 공개한다.
- 인증·권한, 녹화, 전문가 배정은 구현하지 않고 Think 항목으로 분석한다 (#26).
